## Gaps relative to the diagnostic needs

| Required diagnostic datum | Present in default qlog? | Remarks |
|---------------------------|--------------------------|---------|
| **Packet‑generation timestamp** (when the application finishes building the packet) | **Yes** – represented by `send_at_time` (the moment `Connection::send` finishes) |
| **Intended pacing deadline** (value from `SendInfo.release.time(now)`) | **No** – not emitted by the current qlog implementation |
| **Socket‑send entry timestamp** (when `socket.send_to` is invoked) | **No** – not emitted |
| **Socket‑send completion timestamp** (when the sys‑call returns) | **No** – not emitted |
| **Physical‑wire departure timestamp** (as observed by a packet‑capture NIC timestamp) | **External** – requires a separate capture (e.g., `tcpdump -j` or hardware timestamps) |

## Minimal qlog‑compatible extension that would close the gap

Add two optional floating‑point fields to the `PacketSent` struct:

```rust
pub struct PacketSent {
    // ... existing fields ...
    pub intended_release_time_ms: Option<f32>,   // value of `SendInfo.release.time(now)` when available
    pub socket_send_time_ms: Option<f32>,       // timestamp taken immediately before the `socket.send_to` call
}
```

Both values would be expressed as milliseconds elapsed since the connection start (the same reference used for `send_at_time`). Emitting them would allow a downstream analysis tool to compare the intended pacing deadline with the actual socket‑submission time, thereby detecting any host‑side delay after packet preparation.
