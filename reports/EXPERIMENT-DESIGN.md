# Experiment Design (Research Checkpoint 001)

**Purpose** – To compare four configurations and assess whether the *unchanged* quiche qlog contains sufficient information to distinguish intentional pacing from host‑side delay after packet preparation.

The design is deliberately **non‑intrusive**: it relies on the existing quiche binary, the default qlog output, and an optional external packet capture. No source‑level instrumentation is applied at this stage.

## Test matrix

| Config | Description | Expected effect on timestamps |
|--------|-------------|--------------------------------|
| **A – Normal** | Server runs with default pacing (enabled) and without any artificial delay. | `intended_release_time` ≈ `socket_send_time` (difference only due to kernel queueing) |
| **B – Pacing disabled** | Server started with `--disable-pacing` (or equivalent config) so packets are sent immediately after generation. | `intended_release_time` not applicable; `socket_send_time` follows packet generation closely |
| **C – Host delay only** | After `Connection::send` returns, the server thread sleeps for a fixed interval (e.g., 20 ms) **before** invoking `socket.send_to`. (This step is **not** performed yet – it will be added later once the baseline is verified.) | `socket_send_time` will be offset by the injected delay relative to `send_at_time` |
| **D – Combined** | Both pacing enabled **and** host‑side delay injected (as in C). | `socket_send_time` delayed; `intended_release_time` may still be earlier (set by pacing logic) |

## Measured quantities (per packet)

1. **`send_at_time`** – already present in qlog (`PacketSent.send_at_time`).
2. **`intended_release_time`** – would be extracted from the `ReleaseDecision` inside `SendInfo`. *Not present in current qlog* – requires extension (see `QLOG-GAP-ASSESSMENT.md`).
3. **`socket_send_time`** – timestamp taken immediately before the `socket.send_to` system call. *Not present* – requires extension.
4. **`wire_timestamp`** – capture timestamp from `tcpdump -j` (or similar) on the experimental interface. Provides the actual NIC egress time.

## Data collection workflow (baseline – Config A)

1. **Start the server** (see `reports/EXECUTION-PATH-AUDIT.md`). Ensure `QLOGDIR` points to a writable directory on the sender.
2. **Run the client** on the receiver VM, requesting a sufficiently large file (e.g., 100 MiB) to generate many packets.
3. **Capture packets** on the experimental interface of the sender (once it is up) using a command such as:
   ```bash
   sudo tcpdump -i ens4 -w /tmp/trace.pcap -U -s 0 udp port 4433
   ```
   The `-U` flag forces packet‑buffer flushing so timestamps are as close to NIC egress as possible.
4. **After the transfer**, collect:
   - All qlog files from `$QLOGDIR`.
   - The pcap file.
   - The received file checksum on the client side (e.g., `sha256sum`).
5. **Analyse** – For each `packet_sent` event in qlog, match the packet number to the corresponding packet in the pcap (the QUIC packet number is encoded in the packet header). Compare:
   - `send_at_time` (generation) vs. pcap timestamp (wire).
   - (When extension is added) `intended_release_time` vs. `socket_send_time`.
   The offset distribution will reveal whether additional host‑side delay exists beyond what pacing already accounts for.

## Success criteria

*If* the unchanged qlog (`send_at_time` only) is sufficient, we would be able to infer the intended pacing deadline **indirectly** (e.g., by observing regular spacing between `packet_sent` timestamps) and detect any out‑of‑band delays by comparing against the wire timestamps. If the offsets cannot be explained without the missing fields, the experiment demonstrates the need for a qlog extension or external observations.
